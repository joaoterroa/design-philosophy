Radius and curve are different decisions

A conventional rounded rectangle joins straight sides to circular or elliptical arcs. The direction joins smoothly, but curvature changes at the join. A continuous treatment changes curvature toward the side.

A mathematical squircle commonly uses exponent four. CSS calls its version corner-shape: squircle, equivalent to superellipse(2). A long box with these corners remains a rectangle with squircle corners; it is not necessarily a whole superellipse.

Apple’s continuous corner style and CSS squircle are separate constructions. We have no evidence that either exactly reproduces Dia. Apple corner styles; CSS Borders Level 4 working draft.

Blue: circular cornerOrange: squircle corner

At the same radius, the CSS squircle keeps more material in the corner and looks squarer. A larger corner extent can compensate. Matching the 45° inset requires about 1.841× the original radius for this particular mathematical comparison. That number is an experiment control, not a design token recommendation.

How the comparison is controlled

For an unclamped circular corner of extent r, diagonal inset is r × (1 − 2⁻¹ᐟ²). For exponent four it is R × (1 − 2⁻¹ᐟ⁴). Equating these gives R/r ≈ 1.8409. This matches one point, not enclosed area, perimeter or perceived softness. CSS may constrain radii when opposing corners cannot fit, notably tiny dashboard bars. A superellipse inset is not generally another identical superellipse, so “inner radius = outer radius − gap” is not an exact universal rule for continuous shapes.

Capture scope and engineering limits

Menu: change the popover silhouette only. Leave the compact platform-style controls, circles and shift strip intact. Banking: change existing buttons, fields, panels, message and help-sheet corners. Keep the message’s asymmetric corner and square sheet bottom. Dashboard: change existing severity/data-end corners only; do not invent new cards, add row gaps or change semantic clipped ends.

Offline headless Chromium 156.0.8078.4, device scale 1, frozen time, reduced motion, identical local fonts and state hooks. No HTTP/HTTPS requests and no console errors during capture. All PNGs contain non-uniform pixels. Menu handover, banking code/error/help and keyboard focus passed. Element-box equality rules out layout movement, but does not by itself prove painted content cannot clip. The rendered light/dark pairs were also inspected.

CSS corner shaping is browser-dependent. The local app copies fall back to ordinary rounded corners when unsupported; the embedded captures preserve the tested appearance. Production work would require platform-specific rendering, focus, hit-test and resizing checks. This study does not identify Dia’s curve formula or prove preference, brand recognition, usability or motion quality.

What I recommend next

Make the next iteration a test of better design selection. The earlier composition experiments changed emphasis, fold coverage and information density. These geometry experiments mainly change edges. The larger opportunity is how the agent chooses the arrangement and character before it perfects details.

  1. Propose one small process change for review. Before fixing tokens, render two materially different compositions of the same critical screen. Compare emphasis, grouping, proportions and task fit. Choose one and explain the trade-off. Two radius or palette variants do not count as different compositions.
  2. Qualify only the rules that obstruct that process. Treat the novelty limit as a learning-cost judgment, and allow surfaces or color when the product benefits. Preserve accessibility, honest states and operational priority. Do not rewrite every reference at once.
  3. Keep a small optional visual reference. A soft, continuous-corner treatment can include a composer, compact settings counterexample and nested object. Describe curve, extent, insets and platform limits. Show a conventional treatment alongside it. Do not prescribe Dia assets, fixed radii or a stylesheet for every product.
  4. After agreement, run a bounded evaluation. Use the same three tasks in isolated environments. Compare the current skill with the small process revision, with two runs per condition: twelve runs total. Keep model, inputs and total work budget equal. Do not enable the soft-corner option by default. Test the selected designs through the same short task states.

Keep in the core philosophy

  • Choose shape and layout for the task and platform.
  • Review relationships among type, dimensions, insets and curves.
  • Compare rendered alternatives before the design becomes fixed.
  • Protect meaning, access and task performance through states.

Keep optional

  • Continuous or squircle corner families.
  • Specific radius values, nesting treatments and materials.
  • Browser Company examples and other visual traditions.
  • Product-specific warmth, density, motion and expression.

Decision gate: keep the process revision if blind reviewers prefer its overall composition on at least two tasks, with no loss in critical-state correctness, accessible controls or dashboard coverage. Use at least three reviewers, judge task fit separately from “looks like Dia,” and record disagreement. This is a small directional test, not statistical proof.

Judge full screens at their intended size first. Then inspect craft details and short transitions. If reviewers only prefer enlarged corners, that supports an optional finish treatment. It does not justify a new universal philosophy rule.

This plan limits the change we must explain. It tests whether the skill helps agents make better choices across products, while leaving room for different visual identities. The skill remains unchanged. No new evaluation agents have run.
